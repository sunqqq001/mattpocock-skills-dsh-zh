# 诊断缺陷（Diagnosing Bugs）

针对棘手缺陷的一套纪律。只有在有明确理由时才跳过某些阶段（phase）。

探索代码库（codebase）时，阅读 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型（mental model），并检查你正在接触区域的 ADR（Architecture Decision Record，架构决策记录）。

## 脱敏（Redact）

本技能要求你展示命令、输出和捕获的产物（artifact）。**先对每个机密（secret）脱敏**：在它的位置写上 `<REDACTED>`。回路要针对环境变量（env var）构建，这样凭据留在环境里，而不是留在你展示的内容里。捕获的产物带有认证头（auth header）：只引用携带信号的那几行。

如果脱敏后的输出不足以诊断缺陷，就直说，并询问用户。

## 阶段 1（Phase 1）：构建反馈回路

**这就是本技能。** 其余一切都是机械性的。如果你有一个针对该缺陷的**紧致（tight）**通过/失败信号（一个能在_这个_缺陷上变红的信号），你就会找到原因；二分（bisection）、假设检验和插桩（instrumentation）都只是在消费它。如果没有这样的信号，盯着代码看多久都救不了你。

在这里投入不成比例的努力。**要激进。要有创造力。拒绝放弃。**

### 构建回路的途径，大致按此顺序

1. **失败测试**，放在任何能触达缺陷的接缝（seam）上：unit、integration、e2e。
2. **Curl / HTTP 脚本**，针对运行中的开发服务器（dev server）。
3. **CLI 调用**，配一份 fixture（夹具）输入，把 stdout 与已知良好的快照做 diff（对比）。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动界面（UI）并在 DOM/console/network 上做断言。
5. **重放捕获的 trace（跟踪）。** 把真实的网络请求 / payload / 事件日志保存到磁盘；在隔离环境中通过代码路径重放它。
6. **一次性 harness（测试装置）。** 启动系统的一个最小子集（一个服务、模拟的依赖），用一次函数调用就能驱动缺陷代码路径。
7. **Property / fuzz 回路。** 如果缺陷是“有时输出错误”，就运行 1000 个随机输入，寻找失败模式。
8. **Bisection harness（二分装置）。** 如果缺陷出现在两个已知状态（提交、数据集、版本）之间，就把“在状态 X 启动、检查、重复”自动化，这样你就能对它 `git bisect run`。
9. **差分回路（Differential loop）。** 让同一输入分别通过旧版本和新版本（或两种配置），然后对输出做 diff（对比）。
10. **HITL（human in the loop，人在环）bash 脚本。** 最后的手段。如果必须由人来点击，就用 `scripts/hitl-loop.template.sh` 驱动_他们_，这样回路仍然是有结构的。捕获的输出会反馈给你。

构建出正确的反馈回路（feedback loop），缺陷就修好了 90%。

### 收紧回路

把回路当作产品来对待。一旦你有了_一条_回路，就**收紧**它：

- 我能让它更快吗？（缓存设置、跳过无关的初始化、收窄测试范围。）
- 我能让信号更锐利吗？（对具体症状做断言，而不是“没崩溃”。）
- 我能让它更具确定性吗？（固定时间、给 RNG 播种、隔离文件系统、冻结网络。）

一条 30 秒的偶发失败（flaky）回路和没有回路相比几乎毫无优势；一条 2 秒的确定性回路才是紧致的——那是调试的超能力。

### 非确定性缺陷

目标不是一次干净的复现（repro），而是**更高的复现率**。把触发器循环 100 次、并行化、加压、收窄时间窗口、注入休眠（sleep）。偶发失败（flake）率 50% 的缺陷是可调试的；1% 的不是——不断提高复现率，直到它可调试。

### 当你确实无法构建回路时

停下来，明确说出来。列出你尝试过的东西。向用户请求：(a) 能复现它的环境的访问权限，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、core dump、带时间戳的屏幕录制），或 (c) 添加临时生产环境插桩的许可。**不要**在没有回路的情况下继续去假设。

### 完成标准：一条能变红的紧致回路

当回路**紧致**且**能变红（red-capable）**时，Phase 1 就完成了：你能说出**一条命令**（一个脚本路径、一次测试调用、一条 curl），并且你已经**至少运行过一次**（展示这条调用及其输出，已脱敏），这条命令要满足：

- [ ] **能变红（Red-capable）**：它驱动真实的缺陷代码路径，并对**用户的确切症状**做断言，因此它能在这个缺陷上变红、修复后变绿。不是“运行不报错”——它必须能够_抓住这个具体的缺陷_。
- [ ] **确定性（Deterministic）**：每次运行结论一致（偶发失败缺陷：按上文，固定一个高复现率）。
- [ ] **快速（Fast）**：秒级，而不是分钟级。
- [ ] **代理可运行（Agent-runnable）**：你可以无人值守地运行它；只有在通过 `scripts/hitl-loop.template.sh` 时才有人类在环（human in the loop）。

如果你发现自己在这条命令存在之前就开始读代码构建理论，**停下——直接跳到假设正是本技能要阻止的失败。** 没有能变红的命令，就没有 Phase 2。

## 阶段 2（Phase 2）：复现 + 最小化

运行回路。看着它变红——缺陷出现了。

确认：

- [ ] 回路产生的是**用户**描述的失败模式，而不是恰好邻近的另一个失败。找错缺陷 = 修错东西。
- [ ] 失败可以跨多次运行复现（或者，对于非确定性缺陷，复现率足够高，足以作为调试依据）。
- [ ] 你已经捕获了确切症状（错误消息、错误输出、缓慢的耗时），这样后续阶段可以验证修复确实解决了它。

### 最小化

一旦它变红，就把复现缩小到**仍然变红的最小场景**。**一次一个**地削减输入、调用者、配置、数据和步骤，每次削减后重新运行回路，只保留对失败起承重作用的东西。

为什么值得费这个劲：最小化的复现缩小了 Phase 3 的假设空间（剩下可怀疑的活动部件更少），并在 Phase 5 变成干净的回归测试。

当**每个剩余元素都是承重的**时完成：移除其中任何一个都会让回路变绿。

在完成复现**并且**最小化之前，不要继续。

## 阶段 3（Phase 3）：提出假设

在测试任何假设之前，生成 **3–5 个排好序的假设**。只生成单个假设会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的（falsifiable）**：陈述它做出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让缺陷消失 / <改变 Z> 会让它更糟。”

如果你无法陈述预测，这个假设只是一种感觉（vibe）：丢弃它，或把它打磨锋利。

**在测试之前把排序后的列表展示给用户。** 他们通常拥有能瞬间重新排序的领域知识（“我们刚部署了一个对 #3 的改动”），或者知道他们已经排除的假设。便宜的检查点，巨大的时间节省。不要被它阻塞——如果用户不在（AFK），就按你的排序继续。

## 阶段 4（Phase 4）：插桩

每个探查（probe）必须对应 Phase 3 中的一个具体预测。**一次只改变一个变量。**

工具偏好：

1. **调试器（Debugger）/ REPL 检查**，如果环境支持的话。一个断点胜过十条日志。
2. **定向日志**，放在能区分假设的边界处。
3. 绝不“什么都打日志然后 grep”。

**给每条调试日志打上唯一前缀标签**，例如 `[DEBUG-a4f2]`。最后的清理就变成一次 grep。没打标签的日志存活；打了标签的日志被清除。

**性能（Perf）分支。** 对于性能回归，日志通常是错的。替代方案：先建立基线测量（计时装置、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5（Phase 5）：修复 + 回归测试

在**修复之前**写回归测试，但前提是存在一个**正确的接缝（seam）**。

正确的接缝是指测试能在调用点按缺陷实际发生的方式驱动**真实的缺陷模式**。如果唯一可用的接缝太浅（当缺陷需要多个调用者时只有单调用者测试、无法复现触发缺陷的调用链的单元测试），在那里写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是发现。** 把它记下来。是代码库的架构阻止了这个缺陷被锁死。为下一个阶段标记这一点。

如果存在正确的接缝：

1. 把最小化的复现变成那个接缝上的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始的（未最小化的）场景重新运行 Phase 1 反馈回路。

## 阶段 6（Phase 6）：清理

在宣布完成之前必须做到：

- [ ] 原始复现不再复现（重新运行 Phase 1 回路）
- [ ] 回归测试通过（或缺少接缝的情况已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已被移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 被证明正确的假设写进了提交 / PR（pull request，拉取请求）消息里——这样下一位调试者能学到

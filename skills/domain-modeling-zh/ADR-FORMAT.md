# ADR 格式

ADR（架构决策记录，Architecture Decision Record）存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md`，以此类推。

按需惰性创建 `docs/adr/` 目录：只有在需要第一份 ADR 时才创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这些。一份 ADR 可以只有一个段落。价值在于记录*做出了*某个决策以及*为什么*，而不在于填满各个小节。

## 可选小节

只有当它们确实有价值时才加入。大多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当决策被重新审视时有用
- **Considered Options（考虑过的选项）**：只有当被否决的备选方案值得记住时才写
- **Consequences（后果）**：只有不明显但值得点出的下游影响才写

## 编号

扫描 `docs/adr/`，取最大的现有编号加一。

## 何时提议 ADR

以下三项必须全部成立：

1. **难以逆转**：日后改变主意的成本是实质性的
2. **脱离上下文令人费解**：未来的读者看到代码会疑惑"他们到底为什么这样做？"
3. **真实权衡的结果**：确实存在备选方案，而你出于具体原因选择了其中一个

如果某个决策容易逆转，就跳过：你到时候直接逆转掉就行。如果它不令人费解，没人会疑惑为什么。如果没有真正的备选方案，除了"我们做了显而易见的事"之外就没什么可记录的了。

### 哪些算得上

- **架构形态。** "我们用的是 monorepo（单仓）。" "写模型采用事件溯源，读模型投影进 Postgres。"
- **context（上下文）之间的集成模式。** "Ordering 与 Billing 通过 domain events（领域事件）通信，而不是同步 HTTP。"
- **带有锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都算：只有那些换掉要花一个季度的才算。
- **边界与范围决策。** "Customer 数据归 Customer 上下文所有；其他上下文只通过 ID 引用它。" 明确说"不"与明确说"是"一样有价值。
- **对显而易见路径的有意偏离。** "我们用手写 SQL 而不是 ORM，因为 X。" 凡是合理读者会假设相反做法的东西都算。这些记录能阻止下一位工程师去"修复"一件有意为之的事。
- **代码中不可见的约束。** "由于合规要求，我们不能用 AWS。" "由于合作伙伴 API 契约，响应时间必须低于 200ms。"
- **被否决的备选方案，当否决原因不明显时。** 如果你考虑过 GraphQL，却出于微妙的原因选择了 REST，把它记下来；否则半年后又有人会提议 GraphQL。

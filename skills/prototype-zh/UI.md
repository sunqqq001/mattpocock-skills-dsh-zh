# UI Prototype（界面原型）

在单一路由上生成**几个差异极大的界面变体**，用一个浮动底栏切换。用户在浏览器中来回切换变体，挑出一个（或从每个变体里各偷一点），然后把其余的扔掉。

如果问题涉及逻辑/状态而不是外观长相，那这就是错误的分支。改用 [LOGIC.md](LOGIC.md)。

## 何时适合采用这种形态

- 「这个页面应该长什么样？」
- 「在定稿之前，我想看看这个仪表盘的几个备选方案。」
- 「给设置页试试一种不同的布局。」
- 任何用户本来会花一天时间在脑海里三个模糊样稿之间纠结的情况。

## 两种子形态：强烈偏好子形态 A

当界面原型**紧贴着应用的其余部分**时，评判起来容易得多：真实的页头、真实的侧边栏、真实的数据、真实的密度。孤零零的一条 throwaway（一次性）路由就是真空：每个变体孤立地看都不错。只要存在一个说得过去的现成页面可以承载这些变体，就默认用子形态 A。只有当原型确实没有邻近的容身之处时，才去用子形态 B。

### 子形态 A：对现有页面做调整（首选）

路由已经存在。变体在**同一条路由**上渲染，由一个 `?variant=` URL search param（查询参数）门控。既有的数据获取、参数与鉴权全部保留。只有渲染部分被换掉。这是默认选项；除非有具体理由，否则就选它。

如果原型针对的东西还没有页面，但*天然应该住在某个页面里*（仪表盘的新区块、设置页上的新卡片、现有 flow（流程）中的新步骤），那它仍然是子形态 A。把变体挂载进宿主页面内部。

### 子形态 B：新页面（万不得已之选）

只有当被原型化的东西确实没有现成页面可以容身时才用它（例如一个全新的顶层界面，或一条无法合理地嵌入任何地方的流程）。

按照项目已有的路由约定创建一条 **throwaway 路由**。不要发明新的顶层结构。命名要让人一眼看出它是原型（例如在路径或文件名里包含 `prototype` 一词）。同样使用 `?variant=` 模式。

在敲定子形态 B 之前，先做个 sanity-check（理智检查）：真的没有可以把它嵌进去的现有页面吗？空路由会掩盖设计问题，而有内容的路由会暴露它们。

两种子形态中的浮动底栏完全相同。

## 流程

### 1. 陈述问题并确定 N

默认 **3 个变体**。超过 5 个就不再是差异极大，而开始变成噪音，所以以此为上限。

把计划写成一行，放在原型所在位置或文件顶部的注释里：

> 「设置页的三个变体，通过 `?variant=` 切换，位于现有的 `/settings` 路由上。」

无论用户在场反对还是不在场，这都行得通。

### 2. 生成差异极大的变体

起草每个变体。让每个都满足：

- 页面的用途，以及它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，无论什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：布局不同、信息层级不同、首要 affordance（可供性）不同，而不只是颜色不同。三个微调过的卡片网格不是界面原型，是壁纸。如果两份草稿太相似，就带着明确的「不要用卡片网格」指示重做其一。

### 3. 把它们接起来

在该路由上创建一个切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：让所有的既有数据获取保持在切换器之上；每个变体只改变被渲染的子树。

对于子形态 B（新页面）：`prototype/<name>` 下的 throwaway 路由挂载同一个切换器。

### 4. 构建浮动切换器

屏幕底部居中的一个小型固定定位条，包含三部分：

- **左箭头**：循环到上一个变体（首尾相接）。
- **变体标签**：显示当前变体的键，如果变体导出了名称，也显示该名称，例如 `B (Sidebar layout)`。
- **右箭头**：向后循环（首尾相接）。

行为：

- 点击箭头会更新 URL search param（用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体既可分享，刷新后也保持稳定。
- 键盘：`←` 和 `→` 方向键也能循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于聚焦状态时，不要拦截方向键。
- 在视觉上与页面区分开（例如高对比度的胶囊样式、微妙的阴影），让人一眼看出它不是被评估设计的一部分。
- 在生产构建中隐藏：以 `process.env.NODE_ENV !== 'production'` 或等效检查作门控，这样一次走失的原型合并也不会把底栏带到用户面前。

把切换器放在单个共享组件里，两种子形态都能复用它。把它放在项目中共用界面代码所在的位置。

### 5. 交付

把 URL（以及 `?variant=` 的各个键）亮出来。用户有空时就会来回翻看。有意思的反馈通常是**「我想要 B 的页头，配上 C 的侧边栏」**——那才是他们真正想要的设计。

### 6. 归档答案并清理

一旦某个变体胜出，先归档答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 所述的方式归档原型。把胜出者融入真实代码，把其余的挪到 throwaway 分支上，而不是 main：

- **子形态 A**：把胜出者融入现有页面；从 main 中删除落选的变体和切换器。
- **子形态 B**：把胜出变体晋升为真实路由；从 main 中删除 throwaway 路由和切换器。

整套变体就是 primary source（一手来源），所以它落在 throwaway 分支上，而不是垃圾桶里——因为留在 main 分支里的变体组件和切换器会很快腐烂，并让下一位读者摸不着头脑。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上有分歧。
- **变体之间共享过多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了本意。每个变体都应该有自由抛弃布局。
- **把变体接到真实的 mutation（变更操作）上。** 只读原型没问题。如果某个变体需要变更数据，就让它指向一个 stub（桩）：问题是「它应该长什么样」，而不是「后端能不能跑通」。
- **把原型直接推上生产。** 变体代码是在原型约束（没有测试、最少错误处理）下写成的。把它融入正式代码时，请恰当地重写。

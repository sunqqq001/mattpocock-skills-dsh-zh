# Logic Prototype（逻辑原型）

一个自包含的单个 HTML 文件（一个**可分享的演示**），任何人都能通过点击按钮来驱动某个 state model（状态模型）。当问题涉及**业务逻辑、状态转换或数据形态**时使用本分支：这类东西在纸面上看起来合理，但只有把它推过真实用例之后，才会感到不对劲。

因为它只是一个文件、无需安装任何东西，你可以把它交给非开发人员（设计师、PM、领域专家），让他们亲自感受这个模型。所以它说的是他们的语言，而不是代码的语言。

## 何时适合采用这种形态

- 「我不确定这个 state machine（状态机）能否处理 X 之后又 Y 的那种 edge case（边界情况）。」
- 「这个数据模型真的能让我表达……这种情况吗？」
- 「我想在动手写之前先摸清 API 应该长什么样。」
- 任何想让人**按按钮、看状态变化**的情况。

如果问题是「它应该长什么样」，那这就是错误的分支。改用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，先写下你要原型化的是哪个 state model、什么问题。一段话即可，放在演示的最顶部（放在可见的引言里，而不是仅仅写在注释里）。回答错问题的逻辑原型纯属浪费，所以要把问题写清楚，便于日后核对——无论用户是现在盯着看，还是 AFK（离开键盘）之后回来看。

### 2. 把逻辑隔离进一个可移植的模块

把真正的逻辑（就是回答问题的那部分）放进单个 `<script>` 块中，写成一个小的纯模块——将来可以直接拎出来放进真实代码库。它周围的页面是 throwaway（一次性）的；这个模块不是。

正确的形态取决于问题：

- **纯 reducer（归约器）**：`(state, action) => state`。当 action 是离散事件、state 是单个值时合适。
- **state machine（状态机）**：显式的状态与转换。当「此刻哪些操作是合法的」本身就是问题的一部分时合适。
- **一组小规模的纯函数**，作用于某个普通数据类型。当不存在隐含的当前状态、只有各种转换时合适。
- **一个方法面清晰的类或模块**，当逻辑确实持有持续的内部状态时。

挑选最适合所提问题的形态，而*不是*最容易接到页面上的那个。保持纯性：不碰 DOM，不用 `document`，不允许按钮处理器伸进它内部。页面调用它；没有任何东西反向流动。这正是让原型超越自身寿命的原因：一旦问题得到解答，经过验证的 reducer / machine / 函数集就能自行升格进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：不用框架、不用打包器、不用服务器，全部内联，这样双击就能打开，经得起被邮件来回转发。任何人打开它就能运行。

为一名非开发人员而写。每个标签都用**领域语言**，而不是代码语言：按钮和状态读起来像业务，而不是 reducer。用大白话解释正在发生什么。

用清晰的层级从上到下排布：

1. **标题和一句话说明**：这个演示让你探索什么（即第 1 步中的问题）。
2. **当前状态**：完整的相关状态，渲染成一个可读面板（带标签的字段，而不是原始 JSON 转储），每次点击后重新渲染，让变化看得见。凡是有助于非开发人员跟上的地方，明确指出刚刚发生了什么变化。
3. **自由操作按钮**：每个操作一个按钮，始终可用，任何人都能以任意顺序摆弄这个模型。每次点击派发其操作并重新渲染状态。
4. **引导式走查**：一组 **scenarios（场景）**，每个标签页一个。每个标签页包含对该场景的简短白话描述（它设定的情境，以及要观察什么），其下方是该场景**要按的按钮**的先后顺序。每一步都是一个真实的按钮：点击它就执行该操作并进入下一步。开始一次走查会重置到已知的初始状态，这样场景每次都以相同方式运行。

选择能演示棘手情况的场景——那些在纸面上难以推演的情况：happy path（顺利路径）、一个棘手的 edge case、一次本应非法的尝试。

保持美观但克制：干净的排版、充裕的间距、一种强调色。不要动画、不要花哨把戏：任何东西都不得与状态和按钮抢戏。

### 4. 交付

把文件发给他们，或替他们打开。他们有空时就会点过各个走查并自由操作；有意思的时刻是他们说「等等，那不应该可能」或「咦，我以为 X 会不一样」的时候——那些是_想法_里的缺陷，而这正是全部意义所在。如果他们想要新的操作或新场景，就加上。原型会演化。

### 5. 归档答案与原型

一旦原型回答了它的问题，先归档答案，再按 [SKILL](SKILL.md) 所述的方式归档原型。logic 分支对应的映射：经过验证的 reducer / machine / 函数集升格进真实模块（决策被吸收）；HTML 外壳随行进入那个把原型作为 primary source（一手来源）保留的 throwaway 分支——作为一个自包含文件，它在那里依旧能毫不费力地重新运行。

## 反模式

- **不要写测试。** 需要测试的原型就不再是原型。
- **不要接到真实数据库。** 除非问题明确涉及持久化，否则使用内存状态。
- **不要泛化。** 不要有「要是以后想支持 X 呢」之类的念头。原型只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可拎出。让页面成为纯模块外面的一层薄壳。
- **不要伸手去拿框架、打包器或服务器。** 就一个文件，接收者双击即开；React 应用或开发服务器会毁掉「可分享」这一属性。
- **不要把 HTML 外壳送进生产。** 这个页面是为手工逐一点击而优化的。它背后的逻辑模块才是值得保留的部分。

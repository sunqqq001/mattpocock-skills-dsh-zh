# Ask Matt

你记不住每一个技能，所以问吧。

一条 **flow**（流程）是穿过各技能的一条路径。大多数路径沿一条 **main flow**（主流程）展开，并有两条 **on-ramp**（入口）汇入其中。其余一切要么独立存在，要么是运行在其下的一层 vocabulary（词汇）。

## 主流程（Main flow）：idea → ship

大多数工作所走的路线。你有一个想法，想把它构建出来。

1. **`grill-with-docs`** 通过访谈打磨想法。只要你**在工作目录中工作**，就从这里开始：它是有状态的，会把学到的东西保留在 `CONTEXT.md` 和 ADR（架构决策记录，Architecture Decision Record）中。（没有工作目录？改用 `grill-me`，见“独立技能（Standalone）”一节。两者运行的是同一个 `grilling` 原语；`grill-with-docs` 是留下书面记录的那个，因此只要有仓库可供它留下记录，它就是两者中更好的选择。）
2. **分支：每个问题都能在对话中解决吗？** 如果一个问题需要一个可运行的答案（状态、业务逻辑、一个你必须亲眼看到的界面），就绕道经过一个原型（prototype），往返都由 **`handoff`**（交接）桥接（原型住在自己的目录里，这正是 `handoff` 的用途；见“阶段边界（Phase boundaries）”一节）：
   - 用 **`handoff`** 交接出去，然后针对那个文件开启一个全新的会话，
   - 用 **`prototype`** 以一次性代码回答这个问题，
   - 用 **`handoff`** 把你学到的内容交接回来，并在最初的想法线程中引用它。
3. **分支：这是一个多会话构建吗？**
   - **是** → 先 **`to-spec`**（把线程变成规格），再 **`to-tickets`** 把它拆成 tracer-bullet（曳光弹式）票据，每个票据都声明自己的 **blocking edge**（阻塞边界）。在本地追踪器上，每个票据是 `.scratch/<feature>/issues/` 下的一个文件，手工按 blockers-first（阻塞项优先）处理；在真正的追踪器上，这些边会变成原生的阻塞链接，因此任何阻塞项已完成的票据都可以被认领：每个票据启动一次 **`implement`**，在每次之间 **`/clear`** 上下文。每个票据都是自包含的，所以最后一个的上下文可以丢弃。
   - **否** → 就在这里、在同一个 context window（上下文窗口）里运行 **`implement`**。

   无论哪种方式，**`implement`** 都会在内部驱动 **`tdd`** 构建每个议题——一次一个 red-green（红绿）切片——然后在提交前，通过运行 **`code-review`**（对差异的双轴审查：Standards + Spec）收尾。当你只想在没有完整规格的情况下、以 test-first（测试先行）的方式构建一个具体行为时，单独使用 **`tdd`**；当你想针对一个固定的基准点审查分支或 PR（拉取请求，pull request）时，单独使用 **`code-review`**。

### 上下文卫生（Context hygiene）

把第 1–3 步保持在**一个不间断的上下文窗口**中（在 `to-tickets` 之前不要 compact 或 clear），这样访谈、规格和票据全都建立在同一个思考之上。之后每个 `implement` 都从票据出发、以全新状态开始。

这上面的限制是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**（智能区间）：模型仍能敏锐推理的窗口（在最先进的模型上约 150k tokens）。如果一个会话在 `to-tickets` 之前逼近这个窗口，不要以退化的状态硬撑；在最近的 phase boundary（阶段边界）处 `/compact`，然后继续（见“阶段边界（Phase boundaries）”一节）。

## 入口（On-ramps）

一种产生工作、然后汇入主流程的起始情境。

- **缺陷和请求堆积** → **`triage`**（分诊）。它让议题经过分诊角色流转，产出 agent-ready（代理就绪）的议题，之后由 **`implement`** 接手。

  分诊只适用于**并非你创建**的议题：缺陷报告、新进来的功能请求、任何未经加工就到达的内容。`to-tickets` 产出的票据已经代理就绪，所以**不要对它们分诊**。

- **有什么东西坏了** → **`diagnosing-bugs`**。针对那些棘手的：一眼看不透的缺陷、间歇性的 flake（偶发失败）、在两个已知良好状态之间悄悄潜入的回归。在拥有 **tight feedback loop**（紧致的反馈回路）——一条已经能在*这个*缺陷上变红的命令——之前，它拒绝理论化；然后带着 regression test（回归测试）修复。当真正的发现是没有好的 seam（接缝）来锁死这个缺陷时，它的事后复盘会交接给 **`improve-codebase-architecture`**。

- **庞大而模糊的工作：greenfield（绿地）项目或巨大的功能构建，大到一次会话装不下** → **`wayfinder`**，这里认知负荷最高的流程。当从这里到目的地的路还看不见时，它会在议题追踪器上绘制一张由 **decision ticket**（决策票据）组成的 **shared map**（共享地图），一次一个地解决它们，产出**决策，而不是 deliverable（交付物）**，直到迷雾被推开、道路清晰。`grill-with-docs` 打磨的是你能在一次会话中把握的想法，wayfinder 针对的是你把握不了的想法，它更慢、更密集，所以只在恰好这种情形下使用它，绝不要用于范围明确的功能。

  当地图清晰后，**它交接出去，而不是亲自构建**：在主流程的 **`to-spec`** 处汇入，`to-spec` 会把地图上相互关联的决策折叠成一份可构建的计划，然后照常走 `to-tickets` 和 `implement`。把地图直接循环进 `implement` 会跳过那次折叠，丢掉相互关联的细节，所以只有当工作量确实很小时才直接进入 `implement`。

## 代码库健康（Codebase health）

不是功能工作，只是日常维护。

- **`improve-codebase-architecture`** 只要你有空闲时间就运行，让代码库保持适合代理操作的状态。它会浮现 **deepening opportunity**（加深机会）；挑一个就会_产生一个想法_，你可以把它带进主流程的 `grill-with-docs`。它是找出候选者的勘察；**`codebase-design`**（见下文）是你设计所选候选者的工作台。

## 底层的词汇（Vocabulary underneath）

两个 model-invoked（模型可调用）的参考，运行在其他技能*之下*，各自是其词汇的唯一事实来源。当问题出在**词语**而不是流程上时，直接使用它们；或者让上面的技能把它们拉进来。

- **`domain-modeling`**：打磨项目的*领域*语言：质疑一个模糊的术语，解决一个过载的词（一个 “account” 承担三份职责），把难以逆转的决策记录为 ADR。它是 `grill-with-docs` 驱动的主动纪律，让 `CONTEXT.md` 保持为一份干净的 glossary（词汇表）。
- **`codebase-design`** 是 deep-module（深模块）词汇（module、interface、depth、seam、adapter、leverage、locality），用于设计一个模块的*形态*：在干净的接缝处，小接口背后承载大量行为。`tdd` 和 `improve-codebase-architecture` 都使用这套语言。

## 阶段边界（Phase boundaries）

**phase**（阶段）是会话内的一块工作：访谈、实现、QA 都是。在两个阶段的 **boundary**（边界）处你有五个选项，在它们之间做选择是整张地图中最模糊的决策：

- **Continue**（继续）：留在原地。不花成本，也不丢东西。
- **`/clear`**：清空窗口，当这里的内容对接下来无关紧要时。
- **`handoff`** 写一个可移植的 markdown 文件。用途很窄：只用于**新的 harness**（运行环境）、**新目录**、**同事**，或者**在阶段中途**分叉出一个支线任务。它买来的是可移植性。
- **Subagent**（子代理）：把一个范围紧凑的任务送到它自己的窗口，拿回一份报告。
- **`/compact`** 压缩这份上下文，并用它开启一个全新的会话。这是**默认选项**，位于决策树的底部，而不是首选。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序的决策树：五个问题、每个分支背后的推理，以及为什么 primary source（一手来源）的成本让 **Continue**（继续）成为第一个要排除的选项。要在边界**处**做决定；在阶段中途，要么继续，要么把其余部分拆给子代理。

## 独立技能（Standalone）

完全脱离主流程。

- **`grill-me`**：与 `grill-with-docs` 一样不留情面的访谈，但它是 **stateless**（无状态）的：不在本地保存任何东西，也不构建 `CONTEXT.md`。当你**不在工作目录中工作**时使用它（打磨一个计划、一个设计、一篇文章，任何底下没有仓库的东西）。如果你在工作目录中，改用 `grill-with-docs`：它运行同样的访谈并留下书面记录，所以严格来说它是更好的那个。
- **`grilling`** 是访谈原语本身：rounds（轮次）、frontier（前沿），事实是代理的活，决定是你的。`grill-me` 和 `grill-with-docs` 是两条具名的入口，`triage`、`wayfinder` 和 `improve-codebase-architecture` 都在内部运行它。只有当你想要不带任何包装的访谈时才直接使用它。
- **`resolving-merge-conflicts`** 逐个 hunk（补丁块）处理进行中的合并或变基冲突，依据**意图**解决——追溯到每一侧的一手来源，而不是挑拣代码行——然后完成操作。它从不运行 `--abort`。独立于所有流程之外：当你已经身处冲突之中时使用它。
- **`prototype`** 是一个小型、一次性的程序，回答一个设计问题：这个 state model（状态模型）感觉对吗，或者这个界面应该长什么样。一次性（throwaway）是对代码编写方式的约束，而不是销毁它的承诺：答案会折叠进真正的代码，原型本身则作为**一手来源**保存在主干之外的 `prototype/<name>` 分支上，由实现议题指向它。它是主流程第 2 步中的绕行，但任何时候只要一个设计问题难以在纸面上解决，就可以使用它。
- **`research`**：把阅读类的跑腿活委托给一个**后台代理**：它针对**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它阅读期间你继续工作。它产出的文件是要*带进*主流程 `grill-with-docs` 的东西，因为研究喂养思考，而不是取代思考。
- **`to-questionnaire`** 在挡住你的东西不在你的头脑里、也不在代码库里，而在**别人的头脑里**时登场，它为对方写一份问卷来填写。它是 `grill-me` 的反向操作：不是就主题访谈你，而是就 **send**（发送）访谈你（问卷发给谁、你需要收回什么），并让问题瞄准那个缺口。收回来的东西是 `grill-with-docs` 或 `to-spec` 的素材。
- **`wizard`**（向导）用于只有**人类**才能完成的步骤：配置基础设施、设置凭据或 CI 密钥、点击浏览一个陌生的第三方面板、运行一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，并写入 `.env` 和 GitHub secrets，这样该流程就不再需要你每次向代理重新解释。它是模型可调用的，所以代理一撞上只有你才能通过的墙就会用它。如果代理自己能做，它就应该自己做；这个技能用于人类真正 in the loop（在环）的场景。
- **`wait-what`** 是针对一条没被听明白的消息的纠偏手段。在对话中途、任何其他技能内部使用它，代理会用你缺失的上下文、以平实的英文、使用 `CONTEXT.md` 的词汇，重新表述它刚才说的话。它在事后起作用；`grill-with-docs` 才是前期的解药，因为尽早商定的共享语言正是阻止行话出现的根本。
- **`teach`**：跨多个会话学习一个概念，把当前目录当作有状态的工作区。
- **`writing-for-agents`** 是编写代理要消费的文档的参考：技能、AGENTS.md、被指向的文档。

## 前置条件（Precondition）

**`setup-matt-pocock-skills`**：在第一次运行工程流程之前运行，以配置其他技能所依赖的议题追踪器、分诊标签和文档布局。自定义的议题追踪器同样可用。
